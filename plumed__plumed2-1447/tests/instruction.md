# Round to base ten only what the user writes in base ten

**Branch:** `put-round-to-base-ten-v2.10` → base `v2.10` · **Follows:** #1419, #1417
**Stacked on #1445**, which carries the `NaN` fix in the same function, and should be merged first. This PR adds only one .

> **Disclaimer.** This PR was entirely generated by Claude, supervised by @invemichele.

##### Description

When the MD code passes scalars as `float`, `DataPassingObjectTyped<float>::saveValueAsDouble`
rounds them to 7 significant figures, so that a timestep the user wrote as `0.002` does not reach
PLUMED as `0.002000000094995` (#1419). The rounding is currently applied to every scalar, and the
decimal grid it snaps to is anchored to powers of ten while the float grid is anchored to powers of
two, so on a quantity that the MD code *computes* it can be up to 16 times coarser than the float
it is rounding, and discards up to 4 bits. The potential energy is such a quantity, and with
GROMACS in mixed precision `ENERGY` was landing on average 6 ULP away from the value GROMACS holds.

Rounding is now asked for explicitly, with a new `ROUND_TO_BASE_TEN` flag on `PUT`, and the
timestep is the only quantity that asks for it, being the one #1419 was about and the only one the
user writes in base ten:

```cpp
readInputLine("timestep: PUT UNIT=time PERIODIC=NO CONSTANT ROUND_TO_BASE_TEN", true);
```

`kBT` was rounded too, which #1419 described as "probably less critical [...] hopefully harmless";
it now reaches PLUMED as the engine wrote it. Everything else was already unaffected, since arrays
keep the pointer of the MD code and `EXTRACV` values are `MUTABLE` and take the pointer branch.

(Declaring `ENERGY` `MUTABLE` as well would send it down that same pointer branch and skip the
conversion altogether, but it would trade a snapshot for a lazy read: the backup branch captures
the value at the instant the MD code says the energy is valid, while the pointer branch reads the
memory of the engine whenever PLUMED next reaches `wait()` — and since `wasset` is never cleared, 
that read happens on every later step too, including the ones where GROMACS has zeroed `term[F_EPOT]`. 
It would also declare that PLUMED may write into the energy of the engine, which it
never does, and it would leave the conversion wrong for the timestep and for any scalar a user
passes through `PUT`.)

The rounding arithmetic itself is left alone. `std::to_chars` would express it better, writing the
shortest decimal that reads back as the same float rather than guessing seven digits, but
floating-point `<charconv>` needs GCC 11 or libc++ 14 and is gated by the deployment target on
macOS, which seems much for a maintenance branch. Happy to do it on `master` if you would like it.

**Verification**

With GROMACS 2024.3 in mixed precision, printing what PLUMED holds:


|                | PLUMED before  | PLUMED now     | what GROMACS holds |
| -------------- | -------------- | -------------- | ------------------ |
| `timestep`     | 0.002000000000 | 0.002000000000 | 0.002000000094995  |
| `kBT` at 300 K | 2.494339000000 | 2.494338750839 | 2.494338750839233  |


Over a 251-step run with `ENERGY` printed every step at `%.10f`, all 251 values are now exactly a
`float`, against 6 of 251 before, and the largest disagreement with the `Potential` of the `.edr`
drops from 0.005 kJ/mol to 5 × 10⁻⁷, which is the printing precision of the energy file. The two
runs have bit-identical trajectories, so the conversion is the only difference. `regtest/basic` and
`regtest/opes` are unchanged (`rt-average` fails before and after, on this machine, for unrelated
reasons).


The first line is the double kernel, where the flag is a no-op. On the second, `dt_round` is the
clean timestep of #1419, `en_plain` is the exact float, and `en_round` shows the digits the
rounding costs. Nothing covered this path before: the suite otherwise runs the double kernel only,
